# Protocol evidence gaps

The command builders cover all91 official Bluetooth command pages. These gaps concern absent media formats, ambiguous source fields, and physical compatibility. They are not hidden behind a claim that every Divoom model works.

| Area | Implemented | Remaining evidence |
| --- | --- | --- |
| Native image and animation | Checked AA16/32 encoder and decoder, static44 wrapper, standard and Max49 counters, Max flag records, first-seen palettes, per-frame delays | The official pages name an encoder without defining it. The codec uses Go golden fixtures and inherited Max observations. Native64 frame flags and palette layout remain unknown. `Dimension::SixtyFour` can load or resize pixels but native encoding returns `Unsupported`. |
| Native87 text | All seven controls, font sizes, display boxes, colors, speed, text-input and glyph structures, encoded content transport | `divoom_image_encode_frame_word` serialization and maximum word count are unpublished. `EncodedWordFrame` accepts external encoder bytes. It does not serialize `WordInfo` by guessing C memory layout. Host bitmap text rendering works separately. |
| Large64 files | All8D controls, bounded complete transfer,8E list collection and checked pagination | 8D omits FileId width. Four-byte LE IDs can be explicitly selected from8E evidence; arbitrary device-confirmed bytes are supported. No physical64 device test or native64 asset encoder. |
| Drawing and sand painting | All controls, typed RGB and counts, caller-selected offset encodings, movie frames and multicanvas transfers | Offset widths are omitted.5B and5C omit length widths.58 byte ordinals conflict with array indices. APIs require explicit layout selections rather than claiming one is authoritative. |
| Alarm reply layout | Ten-record42 decoder with explicit `AlarmReplyLayout::Page247` selection | Page246 refers to absent `SPP_SET_ALARM_TIME_EXT2`. The ten-byte layout is elected from page247, not established by the missing EXT2 definition. |
| SD names and password characters | Complete length and record parsing with raw Unicode bytes; password encodings selected explicitly | Some examples conflict about Unicode byte order and ASCII versus numeric password digits. SD list items retain name bytes; password choice is visible. |
| Response wrappers | Acknowledged replies and status-less13,14,17 notifications; literal04/15 request variant from pages180 and214 | The SD query tables appear to use a reply wrapper as a request. The library follows the literal documented table, with that discrepancy exposed in coverage. |
| Completion | Max8C captured46 status; bounded8B barrier; B1 and8D policies | No universal final storage ACK or power-cycle persistence guarantee. Unsupported ACK assumptions are not imposed by default. B6 count is unreliable for Max indexed storage. |
| Model behavior | Explicit family profiles, dialects, counter selection and evidence map | Many selection ranges, firmware capabilities, and optional hardware features are absent from the official pages. Audio, SD, FM, alarms, games, sleep, and sensor setters were not exercised on the Max. |
| Platforms | Native Windows and Linux RFCOMM; optional btleplug BLE with discovery | macOS Classic IOBluetooth integration is not implemented. macOS BLE compiles but has no physical test. Linux Classic compiles but has no physical test. BLE initialization beyond the documented envelope varies by family and is not silently guessed. |

Searches inspected the pinned Go source, the substantial Rust reference and its command-source catalogue, and public searches for the exact native encoder identifiers. No definition of the native64 or word encoder was found. A vendor SDK, licensed encoder implementation, or app wire capture would provide the missing evidence. The library already transports such externally encoded assets without changing its session API.
