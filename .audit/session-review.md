# Session and framing correctness review

Reviewed `src/protocol.rs`, `src/session.rs`, `src/transport/windows.rs`, and `src/transport/linux.rs` against `.audit/official-146.json`, `rust/docs/official/{293,294,296,297}.json`, `.audit/official-storage-reference.md`, and `.audit/save-command-live-final.log`. No hardware was contacted. Root was concurrently implementing fixes; line numbers below identify the reviewed pre-fix source, so use symbols when reconciling.

## Findings

1. **P1: Prior unsolicited replies can falsely complete a new transfer** (`session.rs`, `transfer_inner`, lines 308–325; `service_retransmissions`, lines 334–342). Completion and retransmission searches use the entire long-lived public event queue, while `exchange` merely moves older replies into that queue. Reproduction: queue a successful 46/custom05 reply before starting an indexed Max save, supply B1 readiness after start, then provide no completion after end. `transfer_file` reports success using the old status. A stale same-opcode retransmission request can similarly replay an unrelated old chunk number or poison a legitimate new transfer. Scope transfer replies to the current operation; accept completion only after its latest terminator. Isolated test: `stale_custom_mode_falsely_completes_new_save`.

2. **P2: Volatile retries invalidate the only communication barrier** (`session.rs`, `transfer_inner`, lines 303–311). The 8B path issues one 46 query after its original terminator. If the query receives a chunk retransmission request followed by its status reply, the loop replays the chunk and end, then accepts that earlier status. The receipt claims a communication barrier even though the barrier precedes the last two writes. Reproduction requires one native byte: writes start/data/end/query; return one buffer containing 8B/55/[1,0,0] then 46/55/[5]; the method succeeds after six writes, with no query after the final end. A fresh barrier must follow every replayed terminator; merely rejecting the old reply causes a timeout. Isolated test: `volatile_barrier_can_precede_replayed_terminator`.

3. **P2: One poll-slice write timeout terminates an otherwise live operation** (`session.rs`, `write_all`, lines 172–178). A 1-second operation gives the transport at most 20ms per write, but only Interrupted is retried. If native RFCOMM is backpressured for 21ms, `wait`/`ready` returns TimedOut before invoking send, and the session exits with `Error::Io` and becomes poisoned, with almost its entire operation budget unused. A readiness race that returns WouldBlock has the same effect. The native backend has made zero progress in these cases. Specify zero-progress semantics for retryable transport errors and retry them until the actual deadline, or otherwise avoid replacing a requested write deadline with a terminal 20ms budget. Isolated test: `one_poll_timeout_aborts_whole_write`.

4. **P2: Exact-capacity input is misclassified as a stream that never settled** (`session.rs`, `drain_available`, lines 150–156). With accepted option `event_capacity=1`, exactly one queued packet is read and retained, then the method unconditionally errors without probing whether another byte exists. An entirely valid stale event therefore prevents the first command from being written and poisons the session even though queue capacity was respected. The same boundary occurs at any configured capacity, and fragmented frames consume the read budget even before generating events. Permit a nonblocking empty probe after the budget/capacity boundary while continuing to reject actual overflow. Isolated test: `one_queued_event_is_misreported_as_unsettled_stream`.

5. **P2: Failed asynchronous Windows connect is never observed** (`transport/windows.rs`, `wait`, line 17; `Rfcomm::connect`, line 41). Connect waits only for write readiness and passes null exceptfds. Winsock reports nonblocking connect success through writefds and failure through exceptfds, so an asynchronous refusal is ignored until the entire caller timeout expires, then reported as TimedOut; the subsequent SO_ERROR read is unreachable for that failure. Use a connect-specific wait that supplies both write and exception sets, then inspect SO_ERROR. This follows the [official Microsoft select contract](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-select), especially its Remarks and writefds/exceptfds summary. No Bluetooth reproduction was run because hardware access was prohibited.

6. **P3: Fatal next_event errors leave health advertised as reusable** (`session.rs`, `next_event`, lines 241–250). Unlike execute and transfer methods, next_event propagates decoder failure, queue overflow, and EOF without poisoning the session. Reproduction: a transport returns EOF to next_event; it returns an error while `is_poisoned()` remains false. After a corrupt frame, the decoder itself is permanently poisoned, so the public health query contradicts the owned decoder state until a later command fails. Route fatal receive errors through the same health transition; an ordinary timeout/empty poll should remain reusable. Isolated test: `next_event_eof_does_not_poison_session`.

## Verification and limits

`cargo test --manifest-path rust/.audit/session-review/Cargo.toml --offline`: **5 passed**, no hardware. These are bug-characterization tests: their success demonstrates the reviewed behavior; they should fail once the corresponding faults are repaired. The independent test crate has its own output directory and did not change root source or tests. Pacing subtraction was separately identified during review; root had already replaced it with saturating subtraction, so it is not listed as an unresolved finding. No additional confirmed checksum, classic framing, BLE envelope, Linux address-layout, or Linux socket ownership fault was found.

The capture establishes one successful 8C transaction: B1 readiness, 43 chunks, terminator, then 46/custom05 completion. It does not establish that an arbitrary 46 already in the event queue confirms a later save, nor that every model emits the same completion. Official page146 describes the host-to-device LE envelope; classic notification decoding is not itself a discrepancy.
